LLM-Mediated Tool-Making in Visual Programming

Customized components for computational design: generating, packaging, and reusing Grasshopper tools from natural-language intent

01 · Paradox

Visual programming lowers the barrier to code, not to tool-making

Visual programming environments such as Grasshopper let designers work with computational logic without writing low-level code. Woodbury describes parametric modeling as a way for a design system to vary while staying internally consistent, Burry frames scripting as a design practice, and Coates treats programming in architecture as computational thinking applied to form, behavior, and generative processes. The shared value is that the translation between design intent and computational logic becomes visible, adjustable, and open to discussion.

Yet as tasks become more complex or personal, default components stop being enough and designers turn to specialized plug-ins. These extend Grasshopper, but they also require adopting systems, data structures, and functions defined by others. The result is two paradoxes: designers spend a lot of time understanding “other’s” systems, and still cannot always find what they want.

02 · Approach

The LLM as a mediator between intent and logic

Recent research positions large language models as mediators between high-level design intent and executable logic. LLMto3D translates text prompts into Python for parametric 3D objects, and “Mediating Modes of Thought” addresses the relationship between natural-language intent and visual programming logic. Later work by Rietschel and Steinfeld examines the reasoning systems that support exploratory computational design, and names two limits this project responds to: one-off script generation and the lack of a sustained user–model feedback loop.

This Field Note proposes an LLM-driven customized component system. In the prototype, a component becomes a technical container that also carries the design intent behind its creation, while the graph serves as a medium for organizing, externalizing, and revising design thinking through dataflow. Supported by semantic intent documentation, designers can repeatedly refine intent and logic, so customized components become part of an evolving personal tool ecosystem.

03 · Workflow

Four Skills: plan, build, package, reuse

The prototype uses Codex with a customized Skill and the Cordyceps Grasshopper MCP bridge (Talley 2026). The process is a four-stage workflow, /gh-plan, /gh-build, /gh-package, and /gh-reuse, each defined as a Skill in a skill.md file for Codex.

1 · /gh-plan: Intention Breakdown. Translates a natural-language request into a structured Intent Record before touching the canvas. Stored as JSON, it defines goals, stages, nodes, inputs, outputs, and dataflow edges. A simple visualization lets the designer review and revise the interpretation, and each output is traced to the designer’s own words in a personal semantic.md file.

2 · /gh-build: Plan Implementation. Transforms the validated Intent Record into a working Grasshopper definition. From its stages and graph structure, the LLM generates customized Python scripts and organizes component groups on the canvas. The components stay visible and editable, so the designer can refine the result through feedback.

3 · /gh-package: Component Storage. After verification and designer confirmation, the implementation is encapsulated as a Grasshopper User Object that preserves the Python code, component interface, semantic role, and package information. The related graph layout is linked to the Intent Record, so a one-off script becomes a reusable tool tied to the process that created it.

4 · /gh-reuse: Memory Recall and Adjustment. Recalls a stored component together with its Intent Record and graph structure, so Codex understands what the component does and how it was used. It can then be placed in a new graph, combined with others, and adapted to a new intention: reuse becomes recalling, adapting, and extending earlier design logic rather than inserting the same tool again.

04 · Demonstration

A Taipei-time adaptive facade

In the demonstration, a single /gh-plan prompt asks for a facade that uses current Taipei local time to calculate solar position and adjust horizontal louver angles. The resulting Intent Record has five stages: Time and Design Controls, Clock and Solar Position, Facade Panel Framework, Adaptive Shading Logic, and Geometry and Operational Feedback.

/gh-build implemented it on the canvas with 31 objects, 42 dataflow connections, and six Python components producing a 12×6 grid of 72 louvers. /gh-package then registered all six components individually as User Objects under Cordyceps → Taipei Facade, recording them as packaged in the Intent Record.

05 · Future Work

Reliability, verification, and designer control

Future evaluation could compare this workflow against existing Grasshopper plug-ins, measuring accuracy, efficiency, usability, and time to a final outcome through performance metrics and user surveys.

The limits also need attention: established plug-ins carry expert knowledge, testing, documentation, and long-term support, and in specialized fields designers may be unable to verify whether LLM-generated logic is correct. Future research should examine how generated components are validated, how their limitations are communicated, and when expert review is required, in order to define where personalized LLM-generated components can support design practice and where established tools and professional knowledge remain necessary.
